# PAGE-E-006 Acceptance Evidence

- Delivered `/e/leads` as a mobile employee acquisition pool backed by persisted PostgreSQL lead entries. Employees can filter lead status, claim available leads, allocate claimed leads to active tenant employees, and convert their own claimed lead into a follow-up task or nurture queue.
- Data and access: migration `025_employee_lead_pool` adds tenant-bound lead records with status, priority, assignee, timestamps and optimistic version. Every read/action resolves the authenticated active employee, enforces tenant and RBAC boundaries, validates inputs, uses idempotency for writes, and records audit plus correlated Outbox events.
- HTTP: `node --test tests/page-e-006-api.test.mjs` launches the production API artifact against PostgreSQL and verifies normal listing, active assignee lookup, claim replay, stale-version rejection, conversion to nurture/follow-up, task creation, batch assignment, owner boundary, unauthenticated rejection, cross-tenant rejection, validation rejection, audit and Outbox persistence.
- Browser: `pnpm.cmd exec playwright test --config playwright.page-e-006.config.ts` passes two 390px Chromium flows. It executes real claim, assignment and nurture conversion against the API, and verifies the no-session recovery view. Screenshots: `employee-lead-pool-mobile.png`, `employee-lead-pool-forbidden.png`; traces are in `playwright-output/`.
- Visual review: the 390px primary state uses clear priority chips, 44px-or-larger actions, status filter, direct action feedback and responsive card layout. The recovery card is readable and provides a return path.
